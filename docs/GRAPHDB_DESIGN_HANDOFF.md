# 금융권 법령 지식그래프 — 설계 핸드오프 문서

이 문서는 **폐쇄망 환경의 LLM에게 지식으로 제공**하여, 여기 서술된 것과
동등한 시스템(대한민국 법령 조문을 지식그래프로 만들고 그 위에 RAG 쿼리
API를 얹는 것)을 처음부터 재구현할 수 있게 하는 것이 목적이다. 특정
리포지토리 경로나 코드를 그대로 재사용하는 게 아니라, **설계 원칙·구조·
겪었던 함정을 그대로 재현**할 수 있도록 서술한다.

---

## 1. 목표와 스코프

**목표**: 금융지주회사 내부통제시스템 RAG 프로젝트의 일부로, 대한민국
금융권 관련 법령(원 프로젝트 기준 33개 법령, 법률/시행령/시행규칙 등
포함 60개 원문 파일)을 **조문 단위 지식그래프**로 만들어, "이 내부통제
기준이 어떤 법조문에 근거하는지"를 추적 가능하게(GraphRAG) 하는 것.

**핵심 요구사항 — 이것이 전체 설계를 결정한다**: 컴플라이언스 시스템
특성상 **"왜 이 관계가 추출됐는지 항상 설명 가능해야 한다"**. 이 요구
때문에 다음이 결정됐다:

- 관계(엔티티 간 edge) 추출은 **LLM이 아니라 결정론적 규칙**(형태소분석 +
  격조사 규칙)으로 한다. LLM 기반 자유형식 추출을 먼저 시도했다가
  "설명 불가능"을 이유로 전면 폐기하고 규칙 기반으로 전환한 히스토리가
  있다.
- LLM은 오직 **"이미 정해진 후보 중에서 고르는" 좁은 역할**에만 쓰고,
  결정론적 규칙이 이미 정한 것(관계의 존재, 방향, 능동/피동, 의무/금지/
  재량)을 절대 재해석·역전시키지 않는다.
- 모든 관계에는 **`extraction_method`**(rule / llm_disambiguation /
  llm_fallback) 감사 추적 필드를 반드시 남긴다.
- **"틀린 데이터"가 "누락된 데이터"보다 훨씬 나쁘다.** 애매하면 채우려
  하지 말고 스킵한다(스킵된 것은 원문 텍스트로 여전히 확인 가능).

## 2. 전체 아키텍처

```
[법령 원문 .md 파일들]
        │
        ▼
┌───────────────────┐
│ 1. 구조 파싱        │  법령 원문 → 조/항/호/목 구조 (결정론적, 정규식)
└───────────────────┘
        │
        ▼
┌───────────────────┐
│ 2. SVO 추출         │  항(項) 텍스트 → (주어, 동사, 목적어, 양상, 태)
│                    │  (결정론적, 형태소분석 + 격조사 규칙 — LLM 없음)
└───────────────────┘
        │
        ▼
┌───────────────────┐
│ 3. edge_type 매핑   │  동사 어근 → 64개 edge_type 중 하나
│                    │  (사전 룩업 우선, 극히 일부만 LLM 분류)
└───────────────────┘
        │
        ▼
┌───────────────────┐
│ 4. 엔티티 타이핑     │  주어/목적어 표면형 → 4개 NodeLabel + subtype
│                    │  (접미사 사전 우선, 실패 시 LLM)
└───────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ 5. 3-store 적재 (RDB가 SSOT, id 발급 주체)      │
│   RDB(PostgreSQL) → AGE(그래프) → OpenSearch  │
│                      (kNN 벡터 인덱스)          │
└─────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────┐
│ 6. RAG 쿼리 API (별도 레이어, 그래프 구축과 분리) │
│   질문 임베딩 → kNN 시드 검색 → 그래프 탐색      │
│   → LLM 답변 생성                            │
└───────────────────────────────────────────┘
```

**규칙/LLM 경계 요약표** (전체 설계의 핵심, 반복해서 강조):

| 단계 | 무엇을 결정하나 | 담당 |
|---|---|---|
| 관계의 존재, agent/patient 배정, 능동/피동, 의무/금지/재량 | SVO 추출기 규칙 결과 그대로 사용 | **규칙(고정, LLM 개입 금지)** |
| 동사 어근 → edge_type(64개 중 하나) | 사전(어근→타입 100% 매핑) 룩업 | **규칙(고정)** |
| 두 갈래 의미로 갈리는 소수 어근의 edge_type 확정 | 절 원문(agent/patient) 안에서 2지선다 | **LLM(좁은 분류만)** |
| 대동사("하다" 등) 문맥 해소 | 문맥 보고 기존 64개 중에서만 선택 | **LLM(좁은 분류만)** |
| 진짜 미분류(사전에도 없는) 어근 | 문맥 보고 기존 64개 중에서만 선택 또는 NONE | **LLM(좁은 분류, 폴백)** |
| agent/patient 표면 텍스트 → NodeLabel + subtype | 고유명사·기관 접미사 사전 우선 | **사전 우선, LLM은 보강** |
| 동일 지시어 통합(별칭) | 별칭 사전 + 접두사 파편화 제거 | **사전만(이번 구현 범위)** |
| RAG 쿼리 시 그래프 탐색 범위(edge_type) 좁히기 | 키워드 사전 → LLM 카테고리 → LLM 정제 | **사전 우선, LLM 다단 보강** |
| RAG 최종 답변 생성 | 검색된 그래프 사실만 근거로 자유 생성 | **LLM(일반 요약, 자유형식 허용)** |

## 3. 그래프 스키마 (고정, 함부로 확장하지 않음)

### 3.1 엔티티 라벨 — 4개, 열린 어휘 대신 라벨 1개 + subtype 속성

노드 타입을 세분화(예: FinancialInstitution/GovernmentAgency/...)하면
라벨이 무한정 늘어나므로, **"무엇인가(존재론적 타입)"만 라벨로 삼고
"이 관계에서 어떤 역할/세부유형인가"는 property로 흡수**한다.

| NodeLabel | subtype 속성명 | 예시 |
|---|---|---|
| `Organization` | `category` | 금융위원회(정부기관), 은행(금융회사) |
| `Person` | `role_hint` | 감사위원, 대통령, 원장 — 특정 직위/역할명 |
| `LegalDocument` | `doc_type` | 법률/대통령령/총리령/고시 |
| `Concept` | `concept_type` | 내부통제, 자기자본, 신용정보 등 추상 개념 |

**설계 노트**: "조문(Article)"은 노드가 아니다. 그래프가 담아야 할 건
법의 "내용"(엔티티 간 관계)이지 "위치"(몇 조 몇 항)가 아니라는 판단으로,
위치 정보는 엣지 속성(`source_law`/`article_no`/`paragraph_no`)으로만
남긴다. 세 번의 재설계 끝에 도달한 결론.

### 3.2 관계 라벨 — 64개, 반대 극성은 분리 유지

동사 그룹핑(같은 방향·같은 법적 효과인데 표현만 다른 동사는 병합)과
극성 분리(APPOINTS↔DISMISSES, PAYS↔BORROWS, RESTRICTS↔EXEMPTS 처럼
반대 방향인 건 절대 합치지 않음 — 합치면 엣지 라벨만 보고 방향을 알 수
없게 됨) 원칙으로, 실제 법령 900여 개 동사 어근을 전수 분류해서 64개로
수렴시켰다.

```
1. 인사/직위: APPOINTS, DISMISSES, RESIGNS, WORKS_AT, DELEGATES_TO
2. 설립/폐지/조직변경: ESTABLISHES, DISSOLVES, MERGES_WITH, DIVIDES_INTO, CONVERTS_TO
3. 소통/보고/공시: NOTIFIES, SUBMITS, DISCLOSES, REGISTERS, REQUESTS, RECORDS
4. 승인/결정: APPROVES, REJECTS, DELIBERATES
5. 위반/제재: VIOLATES, COMPLIES, SANCTIONS, RESTRICTS, EXEMPTS
6. 재산/거래/자금: ACQUIRES, DISPOSES, HOLDS, INVESTS, ISSUES, TRANSACTS_WITH,
   PAYS, BORROWS, LENDS, GUARANTEES, ENTRUSTS_ASSET, CALCULATES
7. 관리/운영/수행: MANAGES, USES, PERFORMS, PROTECTS, SUPPORTS
8. 판단/심사/감독: REVIEWS, SUPERVISES, EVALUATES
9. 법제/규정: PRESCRIBES, ENACTS, AMENDS, ENFORCES, APPLIES_LAW, EXCLUDES,
   DELETES_PROVISION
10. 상태 전이: OCCURS, EXPIRES, TERMINATES, COMMENCES, CONTINUES
11. 기준 비교: SATISFIES, EXCEEDS, FALLS_SHORT_OF
12. 기타 저빈도: AFFECTS, DENIES, CONVENES, GRANTS, LOSES
```

**엣지 공통 속성**: `source_law`, `article_no`(int, 인용 전파로 다중값
가능하게 설계는 해뒀으나 이번 구현에서는 항상 단일값), `paragraph_no`,
`condition`(현재 미구현, 항상 null), `modality`("의무"|"금지"|"재량"|
"없음"), `voice`("능동"|"피동").

**절대 원칙**: 이 4개 라벨/64개 타입을 판단 중에 확장하거나 새로 만들지
않는다. 판단이 안 되는 케이스는 새 카테고리를 만드는 대신 스킵하거나
`llm_fallback`으로 표시하고 넘어간다. (이 원칙을 어기고 싶은 유혹이
드는 순간 — 예: "리스트 멤버십을 표현할 edge_type이 없다" — 은 아래
9절의 실패 사례를 먼저 읽을 것.)

## 4. 파이프라인 상세

### 4.1 구조 파싱 (결정론적, 정규식)

법령 원문 마크다운에서:
- 조문 헤더: `##### 제N조(의M) (제목)` 패턴
- 항 마커: `**①**`, `**②**` (원문자, U+2460~)
- 호 목록: `  1\. 내용` (2~3칸 들여쓰기, 이스케이프된 마침표)
- 목 목록: `    가\. 내용` (4칸 이상 들여쓰기)

부칙(`## 부칙`) 이후는 별도 조문 체계(제1조부터 재시작)라 본문에서
잘라낸다. 개정이력 주석(`<개정 .../삭제 .../전문개정 ...>`)과 장/절
헤더는 노이즈로 제거한다.

### 4.2 SVO 추출 (결정론적, 형태소분석 + 격조사 규칙) — **가장 중요한 부분**

이 프로젝트에서 통계적 한국어 의존구문분석기(예: 딥러닝 기반 DP 모델)를
쓰지 않은 이유: (1) 폐쇄망 이전 계획이 있어 무거운 모델 가중치를 새로
들이면 유지보수 부담이 큼, (2) 100% 결정론적이어야 "왜 이 관계가
추출됐는지" 항상 설명 가능함. 대신 **형태소분석(품사 태깅)만 하고,
격조사(주격/목적격/보조사)를 규칙으로 해석**하는 방식을 쓴다.

항(項) 단위로 처리해야 한다 — 문장 단위가 아니라. 이유: 항이 이어지며
주어가 생략되는 pro-drop이 매우 흔함(예: "①금융회사는 ~해야 한다.
②제1항에도 불구하고 ~자회사등은 하지 아니할 수 있다"). 조문을 항
단위로 쪼개서 항간 주어 상속 규칙을 적용해야 한다.

**핵심 규칙들(전부 실제 법령 문장으로 검증하며 확정, 재구현 시 반드시
같은 우선순위로 구현할 것)**:

1. **주어/목적어 판정**: 격조사(주격 JKS: 가/이, 보조사 JX: 은/는,
   목적격 JKO: 을/를)를 토큰 단위로 추적.

2. **목적어의 화제화(topicalization) 재배정** — 가장 까다로운 규칙:
   "원장은 국회의 동의를 받아 대통령이 임명한다"에서 "원장"은 화제
   표지(JX)만 붙어 있고 진짜 주격은 "대통령이"다. 즉 "원장"은 "임명하다"의
   목적어가 문장 앞으로 빠진 것. 규칙: 한 문장 안에서 **JX(topic)와
   JKS(subj)가 둘 다 나오면 → subj가 진짜 주어, topic은 (아직 JKO가
   없다면) 목적어로 재배정**. JKS 없이 topic만 있으면 topic이 주어.
   둘 다 없으면 이전 항에서 주어 상속(pro-drop).

3. **능동/피동 방향 정규화**: 동사 파생접미사가 "하다/시키다"(능동)면
   문법적 주어=행위자, "되다/받다"(피동)면 문법적 주어=행위대상. 그래프
   엣지는 항상 "행위자→행위대상" 방향이어야 하므로, 피동이면 agent/
   patient를 스왑한다. 이때 **"~에 의하여" 행위자 명시구가 있으면 그걸
   agent로** 쓰고, 없으면 agent=None으로 남긴다(사람이 나중에 채우게).
   함정: "의하다"는 동사(VV)이고 격조사는 그 앞의 "에"(JKB)다 — "의하"를
   격조사로 착각하지 말 것(실제 겪은 버그).

4. **양상(의무/금지/재량) 판정** — 실측 태그 시퀀스 기준(가설과 다를 수
   있으니 실제 형태소분석기 출력으로 검증할 것):
   - **재량** (최우선순위, 다른 것보다 먼저 체크): `NNB(수) + VA(있)` —
     "~할 수 있다" 패턴. 부정이 앞에 있어도("~하지 아니할 수 있다") 재량.
   - **금지**: `EC(지) + VX(아니하|못하)` — "~하지 아니한다/못한다".
     재량 패턴이 없을 때만.
   - **의무**: `EC(어야) + VX(하)` — "~하여야 한다". 위 둘 다 없을 때만.
   - 양상 탐지 범위는 **다음 동사구가 시작되기 전까지로 한정** — 안 그러면
     "A하며 B되지 아니한다"에서 A의 양상 창을 B까지 넘겨보게 되어
     B의 "지 아니한다"를 A의 것으로 잘못 판정한다.

5. **전방조응 주어 공유**: "OO을 거쳐 XX가 명한다"처럼 진짜 주어(JKS)가
   뒤쪽 절에 한 번만 나오고 앞선 절들이 공유하는 경우, 같은 문장 안에서
   뒤에 나오는 JKS 주어를 앞의 agent=None 레코드에 역방향으로 채운다.
   왼쪽→오른쪽 한 번 훑기로는 못 잡으므로 사후 보정(2차 패스) 필요.
   **JKS 출처만 신뢰**(INHERITED/TOPIC까지 역전파하면 다른 문장/항의
   주어가 잘못 새어 들어올 위험이 큼).

**출력**: 각 항/호/목 텍스트마다 (agent, verb_lemma, verb_root, patient,
modality, voice, agent_source) 튜플의 리스트. agent 또는 patient가 없는
레코드는 이후 단계에서 버려진다(관계는 두 endpoint가 다 있어야 성립).

**알려진 미해결 한계**(재구현 시 스코프에서 의도적으로 제외해도 됨,
아래 9절 참고):
- 조건절 텍스트 추출 (제1항에도 불구하고 등 → condition 속성)
- 위임조항 패턴(JKB 패턴 "~은 대통령령으로 정한다"의 위임 대상)
- 준용/적용 감지 + 인용 전파
- 호/목 열거형 목적어 분리, 특히 **명사구가 "ㆍ"(가운뎃점)로 나열된 경우
  전부 놓침** — `_np_run_text`(명사구를 하나로 합치는 함수)가 연속된
  체언(명사) 토큰만 훑기 때문에, "ㆍ"(기호 태그)를 만나면 거기서 멈춘다.
  "회계감사인과 신탁업자의 이사ㆍ감사는 ..."에서 "감사"만 남고
  "회계감사인"/"이사"는 통째로 사라지는 식. **이건 구조적 한계라 이
  모듈을 수정해서 고쳐야 하는데, 실제로 시도해본 결과(9절 참고) 고치는
  것보다 스킵하는 게 나았다.**

### 4.3 동사 어근 → edge_type 매핑

동사(닫힌 집합, 약 1,500종)는 명사와 달리 **전수 분류가 가능**하다는
전제로, 실제 60개 법령 파일에서 나온 모든 동사 어근을 사람이 직접
64개 edge_type 중 하나로 배정했다(913개 어근, 실제 출현 100% 커버).
이 매핑은 정적 사전(어근 문자열 → edge_type 문자열)으로 저장한다.

**어근 분류는 5개 버킷으로 나뉜다**:
1. **ACTION**(913개, 100% 매핑 완료) — 실제 관계를 나타내는 동사.
2. **DEF**(정의, 22개) — "같다", "해당하다", "간주되다" 등 → 관계 아님, 스킵.
3. **REF**(참조, 47개) — "따르다", "관하다", "의하다" 등 → 관계 아님, 스킵.
4. **STATIVE**(상태, 138개) — "필요하다", "정당하다" 등 → 관계 아님, 스킵.
5. **AMBIGUOUS**(7개, 그러나 인스턴스 수는 많음 — "하다" 하나가 9,000회+) —
   대동사라 표면형만으로 edge_type을 못 정함 → **LLM이 목적어 문맥 보고
   64개 중에서 분류**(배치 처리 필수, 인스턴스가 많아서 하나씩 부르면
   끝나지 않는다).

추가로 **needs_context** 플래그가 붙은 어근이 극소수 있다(예: "처분" →
SANCTIONS(행정처분) 또는 DISPOSES(재산처분), 문맥 없이는 구분 불가) —
이것도 LLM이 목적어 텍스트 보고 2지선다.

**재구현 시 반드시 지킬 것**: `else`(어느 버킷에도 없는 경우) 분기를
**"관계 아님으로 간주하고 조용히 스킵"이 아니라 "진짜 미분류(새 문서
에서만 나올 수 있음) → LLM 폴백"**으로 처리할 것. 처음 구현에서는
DEF/REF/STATIVE 버킷을 별도로 로드하지 않고 else 전부를 스킵 처리했다가,
"이건 원래 60개 파일 전수 분류로 다 커버된 건지, 그냥 안 뽑고 있는
건지" 구분이 안 되는 버그가 있었다. DEF/REF/STATIVE 세 버킷을 명시적
집합으로 로드해서 **"이미 확인된 비-관계"**와 **"한 번도 분류 안 된
어근"**을 구분해야 한다.

### 4.4 엔티티 타이핑

명사(엔티티)는 동사와 달리 **개방집합**이라 전수 규칙화가 안 맞는다는
판단으로, 이 단계만 LLM 사용을 허용한다(프로젝트의 유일한 예외).

- **1차: 접미사 사전**. `법률/시행령/시행규칙/고시/훈령/예규/법`로
  끝나면 LegalDocument. `위원회/공사/협회/조합/회사/은행/청` 등으로
  끝나면 Organization. `위원장/이사/감사/대통령/원장/청장/장관` 등
  직위/역할 명사로 끝나면 Person. 도메인 개념 키워드(`내부통제/
  자기자본/신용정보` 등)로 끝나면 Concept. **먼저 매칭되는 규칙이
  이긴다** — LegalDocument 판정을 가장 먼저 시도(오분류 시 가장
  눈에 띄기 때문).
- **주의**: "위법/불법/준법/탈법" 등은 "법"으로 끝나지만 법령이 아니라
  개념(Concept)이므로 블랙리스트로 명시 예외 처리해야 한다.
- **2차: LLM**. 사전에 안 걸린 표면형만 배치로 LLM에 보내 4개 NodeLabel
  중 하나 + 자유텍스트 subtype을 받는다(NodeLabel은 닫힌 4값, subtype은
  열린 어휘 — "값 목록은 아직 확정 안 함"이 원 설계 의도이므로 자유
  생성 허용). LLM도 실패하면 Concept으로 기본 처리.

**동일 지시어 통합(별칭)**: "금융위" = "금융위원회" = "금융감독위원회"
(구 명칭) 같은 명시적 별칭은 작은 사전(dict)으로 결정론적 처리한다.
그리고 **SVO 추출기의 명사구 병합 한계 때문에 생기는 "쓰레기 접두사가
붙은 파편화"** 문제가 실제로 심각하게 발생했다 — 예: "금융위원회"가
"경우금융위원회", "기간동안금융위원회", "때금융위원회" 등 **25개의
별개 노드**로 쪼개졌다(4.2절의 "ㆍ" 문제와 같은 근본 원인 — 앞의
불필요한 명사구가 안 떨어져 나감). 해결책:
- 확정된 소수의 핵심 기관명(금융위원회, 한국은행, 감사원 등)에 대해서만,
- 알려진 "쓰레기 접두사" 목록(해당기간동안/경우/때/등/이상 등, 전부
  일반 수식어/의존명사)을 정확히 매칭할 때만,
- 접두사를 제거하고 정규명으로 취급한다.
- **접미사가 붙은 경우는 절대 건드리지 않는다** — "감사원장"/"한국은행
  총재"는 "감사원"/"한국은행"과 완전히 다른 엔티티(그 기관의 특정
  직위를 맡은 사람)이므로, 문자열이 그 이름을 포함한다고 병합하면
  안 된다. 이 구분(접두사 제거 OK, 접미사는 별개 엔티티) 없이 "포함하면
  병합"으로 갔으면 심각한 오류가 됐을 것.
- 이미 적재된 데이터에 대해서는 **일회성 마이그레이션 스크립트**(엔티티
  병합: 중복 엔티티를 가리키는 관계의 FK를 정규 엔티티로 재연결하고
  중복 행 삭제)가 필요했다.

## 5. 3-store 데이터 모델

### 5.1 ID 스킴 — RDB가 SSOT

- `document_id`/`entity_id`/`relation_id` 모두 UUID.
- **RDB가 ID 발급 주체**. AGE/OpenSearch는 RDB가 만든 ID를 그대로
  재사용만 한다(AGE 노드/엣지의 `id` 속성, OpenSearch 문서의 `_id`).
- `entity_id`는 문서마다 새로 발급하지 않는다 — 엔티티 해석(별칭
  통합)을 거쳐 기존 RDB `entity` 테이블에서 동일 개체를 찾으면 그
  id를 재사용, 못 찾을 때만 새 UUID 발급.
- `relation_id`는 매 SVO 추출 인스턴스(조/항 단위 1건)마다 새로
  발급한다(재사용/중복제거 없음) — 같은 두 엔티티 사이에 같은
  edge_type이 여러 조문에서 반복돼도 각각 별도 relation row/엣지로
  남긴다(조문별 근거 추적 유지).

### 5.2 RDB 스키마 (PostgreSQL) — document/entity/relation 3테이블만

라벨/edge_type별로 테이블을 쪼개지 않고 통합한다(타입은 컬럼으로만
구분). RDB는 모든 메타데이터와 문서 원문의 SSOT.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE document (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_law          TEXT NOT NULL,
    doc_type            TEXT NOT NULL,          -- 법률/시행령/시행규칙 등
    law_mst             TEXT,                    -- 법령 식별 코드(원 소스 API의 것)
    promulgation_date   DATE,
    enforcement_date    DATE,
    competent_ministry  TEXT,
    file_path           TEXT NOT NULL UNIQUE,
    raw_text            TEXT NOT NULL,           -- 원문 전체(그래프에 없는 사실 확인용)
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE entity (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    label         TEXT NOT NULL,   -- Organization/Person/LegalDocument/Concept
    name          TEXT NOT NULL,
    category      TEXT,            -- Organization 전용
    role_hint     TEXT,            -- Person 전용
    doc_type      TEXT,            -- LegalDocument 전용
    concept_type  TEXT,            -- Concept 전용
    aliases       TEXT[] NOT NULL DEFAULT '{}',
    description   TEXT,            -- AGE/OpenSearch로 그대로 나가는 요약문
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_entity_label_name ON entity (label, name);

CREATE TABLE relation (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    edge_type          TEXT NOT NULL,   -- 64개 중 하나
    source_entity_id   UUID NOT NULL REFERENCES entity (id),
    target_entity_id   UUID NOT NULL REFERENCES entity (id),
    document_id        UUID REFERENCES document (id),
    source_law         TEXT,
    article_no         INT[],   -- 인용 전파 대비 다중값 설계(현재는 항상 단일)
    paragraph_no       INT,
    condition          TEXT,    -- 현재 미구현, 항상 NULL
    modality           TEXT,    -- 의무 | 금지 | 재량 | 없음
    voice              TEXT,    -- 능동 | 피동
    evidence_text      TEXT,    -- SVO 추출 원문 절 (감사 근거)
    extraction_method  TEXT NOT NULL,  -- 'rule' | 'llm_disambiguation' | 'llm_fallback'
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_relation_source_entity ON relation (source_entity_id);
CREATE INDEX idx_relation_target_entity ON relation (target_entity_id);
CREATE INDEX idx_relation_edge_type ON relation (edge_type);
CREATE INDEX idx_relation_document ON relation (document_id);
```

`extraction_method`는 컴플라이언스 감사 추적을 위해 **필수** — "이
관계가 규칙으로 나왔는지 LLM 개입이 있었는지"를 항상 구분할 수 있어야
한다는 원칙의 최소 장치.

### 5.3 그래프 DB 스키마 (Apache AGE 또는 동등한 openCypher 그래프 DB)

엔티티가 직접 연결된다(Article 노드 없음). 라벨/edge_type은 RDB와 달리
그대로 유지(그래프 순회 성능/가독성이 목적이므로 통합할 이유 없음).

- 노드: `id`(RDB entity.id 재사용), `name`, 라벨별 subtype 속성
  (category/role_hint/doc_type/concept_type 중 해당하는 것 하나),
  `description`.
- 엣지: `id`(RDB relation.id 재사용), `source_law`, `article_no`,
  `paragraph_no`, `condition`, `modality`, `voice`.
  (`evidence_text`/`extraction_method` 같은 감사용 상세는 RDB에만
  두고 그래프엔 안 싣는다 — 순회 성능/가독성 우선.)

### 5.4 벡터 검색 인덱스(OpenSearch 또는 동등한 kNN 지원 검색엔진)

라벨/edge_type별 인덱스 분리 없이 entity 인덱스 하나, relation 인덱스
하나로 통합.

- `entity` 인덱스: `id`, `name`, `label`, `description`,
  `description_embedding`(dense vector).
- `relation` 인덱스: `id`, `edge_type`, `source_entity_id`,
  `target_entity_id`, `source_entity_name`, `target_entity_name`,
  `description`(예: "은행법 제20조 제3항: 은행 -[HOLDS]-> 지위
  (modality=없음, voice=능동)" 같은 템플릿 생성 요약문),
  `description_embedding`. — **`source_entity_id`/`target_entity_id`는
  원 설계엔 없었는데, kNN으로 relation이 매칭됐을 때 그 endpoint
  엔티티를 그래프 탐색의 시드로 쓰려면 반드시 필요해서 실전에서
  추가했다.**

**임베딩 모델**: 폐쇄망 이전 계획 때문에 OpenAI 등 외부 API 임베딩은
지양하고 **자체 호스팅 가능한 모델**을 쓴다. 실제 선택: ONNX Runtime
기반 로컬 임베딩 라이브러리(예: fastembed류) + 다국어 소형 sentence
embedding 모델(예: `paraphrase-multilingual-MiniLM-L12-v2`, 384차원).
torch/sentence-transformers보다 설치 용량이 훨씬 작고 GPU 없이도
CPU에서 충분히 빠르다(약 28,000개 문서 임베딩에 수 분 내). 모델은
언제든 교체 가능하게 설계하고(임베딩 차원만 kNN 인덱스 매핑과 맞추면
됨), 특정 모델에 강결합하지 않는다.

## 6. RAG 쿼리 API 설계

그래프 구축(2~5절)과 **완전히 분리된 별도 레이어**다. 구축된 그래프를
가지고 자연어 질문에 답하는 쪽.

### 6.1 기본 흐름 (v1, "러프한 전략")

1. 질문을 임베딩.
2. OpenSearch(또는 동등 벡터DB)에서 entity/relation 인덱스 각각
   top-k kNN 검색 → 시드 엔티티 id 집합 구성(relation 히트는 그
   endpoint id들을 시드로 편입).
3. 각 시드에서 그래프 DB로 depth홉 이웃 탐색(`MATCH (n {id})-[r*1..depth]-(m)`).
4. 탐색 결과를 "[법령 제N조] A -[TYPE]-> B (modality=..., voice=...)"
   형태 텍스트로 직렬화.
5. LLM에게 "이 컨텍스트만 근거로 답하라, 없으면 없다고 말하라" 프롬프트로
   답변 생성.
6. 답변 + 탐색된 서브그래프(시각화용 노드/엣지 목록)를 함께 반환.

### 6.2 실전에서 반드시 필요했던 성능 안전장치

**허브 노드 문제** — 실측: 3,900개 엣지를 가진 노드(예: 금융위원회
같은 범용 규제기관)에서 depth=2 순회 1회가 **936초 걸리고 852,873개
row를 반환**했다(동일 저연결 노드는 depth=2가 0.45초). top_k개 시드
중 하나라도 이런 허브 노드면 전체가 멈춘다. **해결**: depth>1 순회
전에 반드시 그 노드의 1홉 degree를 먼저 세는 저렴한 쿼리(`count(r)`,
허브 노드라도 약 1초)를 실행하고, degree가 임계값(예: 300)을 넘으면
그 시드만 depth를 1로 강제 축소한다.

**edge_type 필터링 — 3단계 폴백**:
1. **키워드 사전**(질문에 "임명"이 있으면 APPOINTS/DISMISSES/... 같은
   식으로 미리 만든 한국어 키워드→edge_type 매핑, 결정론적, 즉시).
2. 1단계가 아무것도 못 찾으면 → **LLM이 대분류(edge_type을 앞서 3절
   처럼 12개 카테고리로 미리 묶어둔 것) 중에서 선택**, 그 카테고리에
   속한 edge_type들로 확장.
3. **2단계 결과만** LLM에게 한 번 더 좁히게 함(그 카테고리 멤버들
   중 진짜 관련된 것만) — **1단계(키워드) 결과에는 이 정제를 절대
   적용하지 않는다.** 이유: 실측으로 LLM 정제가 이미 정확한 키워드
   매칭 결과에서 정답 타입(예: "보고" 질문의 NOTIFIES)을 잘못 빼버리는
   사례가 나왔다. 키워드 매칭은 결정론적 규칙인데 LLM이 그걸
   재판단하다 틀리는 건, 이 프로젝트가 SVO 추출기 결과를 LLM이
   재해석 못 하게 막은 것과 정확히 같은 실수 패턴이다. **"규칙이
   이미 맞힌 걸 LLM이 다시 판단하게 하지 않는다"는 원칙을 쿼리
   레이어에도 그대로 적용할 것.**
4. 어느 단계에서든 필터링된 결과가 0건이면 **필터 없이 재탐색**
   (라우팅 실패가 조용히 "근거 없음"으로 이어지면 안 됨).

**AGE 계열 그래프 DB는 `-[r:TYPE1|TYPE2]-` 다중 타입 문법을 지원 안
할 수 있다**(openCypher 표준이지만 AGE 1.5.0에서 실측: 문법 에러).
여러 edge_type을 걸러야 하면 **타입별로 별도 쿼리를 날려서 Python
쪽에서 합칠 것**.

**컨텍스트 길이 제한**: depth를 조금만 높여도(특히 top_k와 결합) LLM
컨텍스트가 순식간에 커진다. 실측: 261,000토큰짜리 컨텍스트가 만들어져
LLM의 262,144토큰 한도를 넘겨 400 에러가 났다. **LLM에 보내는 컨텍스트
줄 수는 하드 캡(예: 300줄)을 걸고, 시각화용으로 반환하는 노드/엣지
수도 별도로(더 여유 있게, 예: 1,000/1,500) 캡을 걸 것.**

**방향성 탐색**(질문이 "A가 B를 하다"처럼 방향이 명확할 때 `-[r]->`만
따라가서 분기를 줄이는 것)은 capability(파라미터)는 만들어두되, **질문
문장에서 방향을 자동으로 추론하는 로직은 신중히 접근할 것** — 잘못
추론하면 정답 엣지를 조용히 놓치는 "안전하지 않은 실패"가 된다(반면
degree 캡이나 edge_type 폴백은 실패해도 "느려짐" 또는 "더 넓게 검색"
정도로 안전하게 저하됨). 진짜 신뢰할 만한 방향 신호(제대로 된 구문
분석 등) 없이는 보류하는 게 낫다.

### 6.3 LLM 호출 시 반드시 지킬 기술적 함정들 (구조화 출력)

이건 그래프 DB나 이 프로젝트에 국한된 게 아니라 **닫힌 후보 집합에서
LLM이 고르게 하는 모든 구조화 출력(JSON schema) 호출에 공통 적용되는
교훈**이다:

1. **enum이 큰(예: 64개) 배열을 "몇 개 골라라" 식으로 요청하면서
   `maxItems`를 안 걸면, 모델이 같은 값을 반복하며 토큰 예산을 다
   써버리는 디코딩 퇴화(degeneration) 현상이 실제로 재현됐다.**
   그리디 디코딩(temperature=0, 결정론성 확보를 위해 이 프로젝트
   전체가 이렇게 씀)은 반복을 스스로 못 빠져나온다 — 반복이 한 번
   시작되면 그 반복된 패턴 자체가 "다음도 반복해야 자연스럽다"는
   신호가 되는 일반적인 신경망 텍스트 생성 현상. **대응**: (a) 스키마에
   `maxItems`를 항상 명시, (b) 후보 집합 자체를 작게(대분류로 먼저
   좁히고 필요하면 2단계로 세분화) 유지 — 후보가 12개 이하일 때는
   같은 문제가 거의 재현 안 됐다.
2. **`uniqueItems` JSON schema 키워드를 특정 vLLM 서버의 guided-JSON
   grammar 엔진이 아예 지원 안 할 수 있다**(실측: `400 Grammar error:
   Unimplemented keys: ["uniqueItems"]` — `maxItems`는 되는데
   `uniqueItems`만 거부됨). 표준 JSON Schema 키워드라고 다 지원된다고
   가정하지 말고, 새 키워드를 쓰기 전에 실제 호출로 먼저 검증할 것.
   중복 제거가 필요하면 스키마 대신 응답을 받은 후 Python에서 `set()`
   등으로 처리.
3. **닫힌 후보로 강제해도, 폴백(빈 배열/실패 시 값)을 항상 준비할 것.**
   이 프로젝트의 모든 LLM 분류 호출은 예외를 잡아서 "규칙 기본값으로
   폴백" 또는 "스킵 + 통계 카운터 증가" 중 하나로 떨어지지, 절대
   예외가 파이프라인 전체를 죽이게 두지 않는다.

## 7. 인프라 / 배포 요건

- **PostgreSQL 계열 두 인스턴스**: 하나는 그래프 확장(AGE 등)이 설치된
  버전(AGE 이미지는 특정 PG 메이저버전에 고정되는 경우가 많음), 다른
  하나는 RDB용(버전 제약 없음, 최신 사용 가능) — 별개 컨테이너로
  분리하는 게 안전(그래프 확장의 버전 고정이 RDB 쪽 업그레이드를
  막지 않게).
- **검색엔진(OpenSearch 등)**: 로컬/폐쇄망 개발 환경이면 보안 플러그인을
  끄고 단일 노드로 띄우는 게 간편. (특정 버전 이상은 "보안 비활성화"가
  설정 파일이 아니라 컨테이너 시작 시 환경변수로만 되는 경우가 있으니
  실제 이미지 문서를 확인할 것 — 잘못 설정하면 초기 관리자 비밀번호
  요구하며 무한 재시작 크래시가 남.)
- **LLM 엔드포인트**: OpenAI 호환 API를 제공하는 자체 호스팅 vLLM(또는
  동등) 서버. **모델 ID를 설정 파일에 하드코딩하지 말고, 매 실행
  시작 시 `/v1/models` 같은 목록 API로 실제 서빙 중인 모델 ID를
  조회해서 쓸 것** — 배포 환경에서 설정된 모델명과 실제 서빙 모델이
  어긋나 404가 나는 문제를 실제로 겪었다.
- **형태소분석기**: 한국어 형태소분석 + 품사 태깅을 지원하는 오픈소스
  라이브러리(이 프로젝트는 Kiwi 계열 사용). 사용자 사전에 도메인
  복합명사(예: "업무집행책임자")를 등록하는 기능이 있으면 활용.

## 8. Windows 환경 특이사항 (해당 시)

개발/배포 환경이 Windows라면 다음을 미리 알아둘 것:

- **비동기 그래프 DB 커넥션 풀(예: psycopg 계열 AsyncConnectionPool)은
  SelectorEventLoop가 필요한데, Windows asyncio 기본 정책은
  ProactorEventLoop다.** 일반 스크립트에서는
  `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())`
  를 코드 최상단에서 호출하면 해결된다.
- **단, ASGI 서버(uvicorn 등)로 API를 띄울 때는 이 방법이 안 먹힐 수
  있다** — 서버 프레임워크가 내부적으로 이벤트루프를 직접 생성하면서
  정책을 무시하고 하드코딩된 로직으로 Windows에서 무조건 Proactor를
  쓰는 경우가 실제로 있었다(`asyncio.run()`이 언제 앱 모듈을 import
  하느냐의 문제가 아니라, 프레임워크가 루프 자체를 만드는 방식의
  문제). **증상**: DB 풀 초기화가 30초 타임아웃으로 실패. **해결**:
  프레임워크의 표준 실행 함수(`uvicorn.run()` 등)를 쓰지 않고, 직접
  `SelectorEventLoop`를 만들어 `asyncio.set_event_loop()`한 뒤 그
  위에서 서버 객체의 `serve()` 코루틴을 `loop.run_until_complete()`로
  구동한다 — 프레임워크의 루프 생성 경로 자체를 완전히 우회.

## 9. 시도했다가 의도적으로 포기한 것들 (재시도 전에 이 절을 먼저 읽을 것)

이 절은 "아직 안 한 것"이 아니라 **"해봤는데 위험/비용 대비 실익이
없다고 결론 낸 것"**이다. 같은 길을 다시 갈 필요 없게 이유를 남긴다.

### 9.1 SVO 추출기의 "ㆍ로 나열된 명사구 미포착" 직접 수정

4.2절 마지막에 언급한 문제(예: "국세청ㆍ관세청ㆍ...ㆍ국가정보원의
소속 공무원") — 목록의 각 항목이 실제로는 문장의 주어도 목적어도
아니고, 다른 명사(예: "협의회")를 수식하는 절 안에 파묻혀 있어서
SVO 추출 결과 어디에도 안 나타나는 케이스.

**LLM 보충 추출을 시도**: (1) 형태소 태그 기반으로 "ㆍ로 이어진 명사구
목록인데 그중 일부가 이미 뽑힌 관계의 agent/patient 어디에도 없는"
문단을 탐지, (2) 그 문단 원문 + 이미 뽑힌 관계를 LLM에 주고 목록
항목이 다른 엔티티와 맺는 관계를 64개 edge_type 중에서 제안하게 함.

**탐지 정밀도를 맞추는 데만 4번의 반복이 필요했다** (전체 코퍼스
26,000여 문단 기준):
1. 순수 정규식(ㆍ로 구분된 텍스트 런): 4,285건 감지 — 거의 다 가짜
   양성(동사 어근끼리 묶인 것 "개정ㆍ폐지", 조문 번호 참조
   "제36조ㆍ제38조", 추상명사 쌍 "학식ㆍ경험" 등).
2. 고유명사(NNP) 태그로만 제한: 31건 — 그런데 정작 동기가 된 예시
   자체를 놓쳤다("국세청" 등이 형태소분석기 사전에 없어서 NNP가
   아니라 NNG로 태깅됨).
3. NNP 또는 NNG로 완화: 다시 3,703건 — 노이즈 재발.
4. NNP/NNG + **"목록의 모든 항목이 기존 엔티티 타이핑용 접미사
   사전(기관/인물 접미사)에 매칭돼야 함"** 게이트: 70건 — 동기 예시도
   잡히고 규모도 적당.

여기까지는 성공적이었다. **그런데 실제로 LLM에게 관계를 제안시켜보니
결과 품질이 안 좋았다**: 테스트한 4개 케이스 중 1개만 답이 나왔고,
그마저 명백히 틀린 edge_type이었다(예: "협의회 구성원"이라는 의미인데
`GUARANTEES`(보증)를 골랐다). 나머지 3개(진짜 타당해 보이는 케이스
포함)는 아예 아무 답도 안 나왔다.

**근본 원인**: 64개 edge_type 중에 "구성원이다/소속이다"(단체
멤버십)에 깔끔하게 맞는 타입이 없다. `WORKS_AT`이 제일 가깝지만
그건 "사람이 조직에 재직한다"는 의미지 "조직이 상위 협의체의
구성원이다"가 아니다. 안 맞는 후보 집합에서 억지로 고르게 하면
모델은 아무거나 고르거나(틀림) 아무것도 안 고른다(누락) — 둘 다 낮은
가치.

**최종 결론**: 이 케이스는 **그냥 스킵한다.** "누락"은 원문 텍스트로
언제든 확인 가능하지만 "틀린 관계"는 컴플라이언스 그래프의 신뢰를
직접 훼손한다. 이 프로젝트 전체가 일관되게 취해온 태도(DEF/REF/
STATIVE 버킷도 스킵, AMBIGUOUS 버킷도 확신 없으면 NONE)와 같은
판단이다. **새 edge_type("소속"/"멤버십" 등)을 추가해서 이 갭을
메우려는 유혹도 뿌리쳤다** — 두 가지 이유: (1) 64개 타입 확장은
이 프로젝트의 절대 원칙 위반이라 별도의 명시적 예외 승인이 필요한
사안이고, (2) 더 근본적으로 **문제 위치가 "맞는 edge_type이 없어서"가
아니라 "SVO 추출기가 애초에 이 명사구를 관계 후보로도 안 올려서"**다
— edge_type을 추가해도 애초에 적용할 관계 자체가 안 만들어진다.

### 9.2 SVO 추출기(4.2절) 자체를 직접 수정

위 9.1절의 문제를 SVO 추출기(명사구 병합 로직) 자체를 고쳐서 풀 수도
있었다 — "ㆍ"/"과"/"와"를 명사구 경계가 아니라 나열 구분자로 인식해서
목록 전체를 하나로 묶거나, 목록의 각 항목을 별도 관계로 전개하는 식.

**시도하지 않고 보류한 이유**: SVO 추출기는 이미 완성돼서 실제 법령
문장으로 여러 차례 검증하며 확정된 결정론적 코드다(4.2절 규칙들이
그 검증의 결과물). 목록 병합 로직 하나를 고치는 것도, **이미 정상
동작하는 나머지 경로에 회귀를 낼 위험**과 **전체 재검증 비용**이
크다. 게다가 재구현해보니 실제 상황은 예상보다 복잡했다 — 어떤
"ㆍ" 나열은 정말 동사 어근끼리(관계 아님)고, 어떤 건 명사 나열인데
그중 일부(마지막 항목만)는 이미 격조사 앞이라 정상적으로 잡히기도
한다. 이런 세부 케이스를 다 커버하는 규칙을 새로 짜고 검증하는 것보다,
**전체 시스템에 대한 "이 모듈은 검증된 걸로 보고 함부로 안 건드린다"는
원칙을 지키는 비용이 더 낮다고 판단**했다. (이 판단은 프로젝트
관계자의 명시적 승인 없이는 내리지 않는 게 맞고, 실제로 이 세션에서도
사용자에게 먼저 물어보고 진행했다.)

**재구현 시 조언**: 이 문제를 정말 풀고 싶다면, SVO 추출기를 처음부터
만들 때 "ㆍ/과/와로 연결된 명사구 나열"을 1급 시민으로 설계에 포함시켜라
(사후에 패치하는 것보다 훨씬 쉽다). 나열된 명사구가 등장하면: (a) 그
나열이 격조사 앞(진짜 주어/목적어 자리)에 있는지 아니면 다른 명사를
수식하는 절 안에 있는지 먼저 구분하고, (b) 전자면 각 항목을 독립된
agent/patient로 전개(같은 동사/양상/태 공유), (c) 후자면 아예 손대지
않는 게 안전하다(9.1절 결론과 동일한 이유 — 적용할 edge_type이
마땅치 않은 경우가 많다).

## 10. 구현 순서 제안 (처음부터 만든다면)

1. **원문 확보** — 법령 원문을 조/항/호/목 구조가 살아있는 형태로
   수집(마크다운이든 뭐든, 구조 파싱 규칙을 여기 맞춰 설계).
2. **구조 파서** (4.1절) 구현 + 실제 원문 몇 개로 파싱 정확도 검증.
3. **형태소분석 파이프라인 셋업** + 법령 코퍼스 전체에서 동사구 빈도
   집계(어근 그룹핑의 근거 자료).
4. **동사 어근 → edge_type 매핑 확정** (4.3절) — 사람이 빈도 상위부터
   직접 분류, 최종적으로 전체 어근 커버리지 100% 확인. 이 작업이
   전체 프로젝트에서 가장 시간이 걸리는 단계이지만, 한 번 제대로
   해두면 이후 모든 게 결정론적이 된다.
5. **SVO 추출기** (4.2절) 구현 — 실제 법령 문장 100개 이상으로 직접
   검증하며 규칙을 다듬을 것(가설만으로 짜지 말고, 실제 형태소분석기
   출력 태그를 확인하며 진행).
6. **엔티티 타이핑 사전** (4.4절) — 명사 빈도 집계 → 접미사 규칙 →
   LLM 보강 순서.
7. **3-store 스키마 + 로더** (5절) — RDB 먼저(SSOT), 그다음 AGE,
   그다음 OpenSearch(임베딩 계산 포함) 순서로 적재.
8. **파이프라인 오케스트레이션 스크립트** — 전체 문서 배치 처리 +
   `extraction_method`별 건수 로그 출력(감사 추적 확인용).
9. **RAG 쿼리 API** (6절) — 그래프가 이미 채워진 뒤에 별도로 구축.
   허브 노드 방지(6.2절)를 처음부터 넣을 것 — 나중에 추가하면 이미
   장애를 한 번 겪은 뒤가 된다.

각 단계마다 결과를 실제 데이터로 검증하고 진행할 것 — 이 프로젝트
전체가 "가설 → 실제 문장으로 검증 → 규칙 수정"을 반복하며 만들어졌고,
가설만으로 다음 단계로 넘어갔을 때마다 나중에 재작업 비용이 컸다.
