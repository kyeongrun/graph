# 그래프DB 파이프라인 설계 로그 (백업, CLAUDE.md에서 분리)

CLAUDE.md가 "5단계"(엔티티 타이핑 + 3-store 적재) 위주로 다음 작업에
집중할 수 있도록, 스키마/파이프라인이 **왜 지금 형태가 됐는지**의 전체
설계 히스토리(반려된 대안, 재설계 3~4회, 버그 히스토리)를 이 파일로
옮겼다. 5단계를 실제로 구현하는 데는 필요 없다 — CLAUDE.md의 "확정된
산출물"/"확정된 그래프 구조"/"svo.py가 이미 해결한 것" 절이 결론만
요약해서 담고 있다. 이 파일은 나중에 "왜 이런 선택을 했는지" 되짚어야
할 때만 보면 된다.

원래 CLAUDE.md의 "지금까지 완료된 파이프라인" ~ "남은 일(미착수)"
섹션을 그대로 옮긴 것이라 이하 번호/톤은 CLAUDE.md 스타일 그대로다.

---

## 지금까지 완료된 파이프라인 (NLP 직접추출, v2)

```
법령 원문 수집 → 형태소분석(동사 파악) → 동사구 어근 정규화
→ REF/DEF/STATIVE 분리 + edge_type 그룹핑(64개, 전수 매핑 완료)
→ 조/항 구조 파싱 + 격조사 기반 SVO 추출(1차 구현 완료)
→ 엔티티(노드) 스키마 설계(4-라벨, 확정) + 그래프 구조 확정(완료)
→ src/graphdb/schema.py를 위 스키마로 교체(완료)
```

### 1단계 — 법령 원문 수집 (완료)
- `data/laws/law_list.txt`: 사용자가 전달한 33개 법령 원본 목록 (오타/약칭
  그대로 보존 — 감사 추적용).
- `scripts/fetch_laws.py`: [legalize-kr/legalize-kr](https://github.com/legalize-kr/legalize-kr)
  (국가법령정보센터 OpenAPI 미러, 법률/시행령/시행규칙별 md + YAML
  frontmatter) 로컬 체크아웃에서 해당 법령만 복사. 사용법:
  `python scripts/fetch_laws.py /path/to/legalize-kr-checkout`
- `data/laws/raw/`: 복사된 원문 60개 md 파일. `data/laws/manifest.json`:
  파일별 법령MST/공포일자/시행일자/소관부처 메타데이터. 33/33 매칭 완료.

### 2단계 — 형태소분석 (완료)
- `src/graphdb/nlp/morphology.py`: **Kiwi**(kiwipiepy) 사용. 법률문은
  대부분 "체언(NNG/NNP/XR) + 하다/되다(XSV)" 결합이라, 이 결합을 하나의
  "동사구"로 합쳐서 센다 (예: "선임"+"하" → "선임하다"). 의무/금지/재량
  같은 양상은 동사구가 아니라 그 뒤 어미/보조용언 사슬에 실리므로, 여기서는
  분리해서 "양상 후보" 버킷에만 모아둔다.
- `data/laws/domain_dictionary.tsv`: Kiwi 사용자 사전 (법률/금융 전문
  복합명사, 예: 업무집행책임자). 미등록 용어 나올 때마다 계속 추가해야 함.
- `scripts/analyze_verbs.py`: `data/laws/raw/**/*.md` 전체 실행 →
  `data/laws/verb_phrase_frequency.json`(동사구 1,490종/113,140회),
  `data/laws/modal_candidate_frequency.json`(양상 후보 어간 있다/되다/없다,
  7,934회 — 문맥 없이는 의무/금지/재량 셋 중 뭔지 판정 불가해 분리 보관).

### 3단계 — 동사구 어근 정규화 (완료, v3)

**주의**: "완료"는 **표면형(선임하다/선임되다 등) → 어근(선임) 정규화만
완료**됐다는 뜻이다. 어근끼리 의미로 묶어 edge_type(그래프 관계 라벨)을
정의하는 작업은 별개이고 3.5단계에서 진행했다.
`scripts/group_verbs.py` → `data/laws/verb_groups.jsonl` (그룹당 1줄
JSONL, 1,127개 그룹).

**설계 히스토리 (왜 v3가 됐는지, 다음에 또 뒤엎지 않으려면 필독)**:
- v1: 사람이 "같은 주제"(예: 준수/위반 둘 다 "컴플라이언스 상태") 기준으로
  50개 미만 그룹으로 수작업 매핑. → 사용자가 "준수하다"와 "위반하다"처럼
  **반대 의미**가 한 그룹에 있으면 그래프 relation label만으로 방향(긍정/
  부정)을 알 수 없다고 지적 (컴플라이언스 시스템에서 치명적).
- v2: 반대 의미 그룹을 전부 분리(44→58개, 50개 제약 폐기). 그런데 이번엔
  "보호지원"처럼 반대는 아니어도 **결이 다른 두 의미**(보호 ≠ 지원)를
  묶은 게 또 지적받음.
- v3(현재): 사람의 "비슷하니 묶자" 판단을 아예 없앰. 동사구가 구조적으로
  "한자어 어근 + 파생접미사(하다/되다/받다/시키다)"이므로, **접미사를
  기계적으로 떼어낸 어근으로 자동 그룹핑**. "보호하다"/"지원하다"는 어근이
  달라 자동 분리, "선임하다"/"선임되다"는 어근이 같아 자동 통합(능동/피동
  차이는 svo.py 섹션 참고). 잡았던 버그: "당하다"를
  접미사로 취급하면 "해당하다/정당하다/부당하다/타당하다/상당하다/
  담당하다"처럼 **어근 자체가 "당"으로 끝나는 흔한 한자어**가 전부
  "정하다"류와 오분류됨 — "당하다"를 접미사 목록에서 제거해 수정.

**verb_groups.jsonl 한 줄 예시**:
```json
{"root": "선임", "count": 216, "members": [{"l": "선임하다", "c": 146}, {"l": "선임되다", "c": 70}]}
```

### 3.5단계 — REF/DEF/STATIVE 분리 + edge_type 그룹핑 (완료)

3단계는 표면형을 어근으로 정규화했을 뿐(예: "선임하다"/"선임되다" →
"선임") 의미 그룹핑이 아니었다. "선임"/"임명"/"지명"처럼 어근은 달라도
그래프에서는 같은 edge_type(예: APPOINTS)이어야 할 동의어들을 이
단계에서 실제로 다 묶었다.

- `scripts/classify_edge_roots.py` → 1,127개 어근을 **REF**(참조/근거
  표현, 47그룹/29.9%) / **DEF**(정의·동일성·법적 의제, 22그룹/10.0%) /
  **STATIVE**(형용사성 서술어=속성 판단이지 관계가 아님, 138그룹/5.0%,
  이 단계에서 새로 발견) /
  **AMBIGUOUS**(대동사 "하다"/"이루어지다", 부정·피동 보조 "아니하다"/
  "당하다"/"않다" 등 — 정적 사전으로 분류 불가, 문맥으로 해소, 7그룹/8.4%)
  / **ACTION**(913그룹/46.7%, 실제 edge_type 대상)으로 분리. 처음엔
  top-300만 훑고 "완료"로 착각했다가 전수 매핑 중 REF/DEF/STATIVE/AMBIGUOUS
  판정 누락분을 계속 찾아내며 이 리스트를 세 번 더 확장했음 — 각 추가분마다
  왜 넣었는지 근거를 주석에 남김(v3의 SUFFIXES 주석과 같은 방식).
- 결과: `data/laws/verb_roots_{ref,def,stative,ambiguous,action}.jsonl`.
- REF 비율(~29~30%)이 미리 적어둔 "28%" 추정치와 거의 일치 — 교차검증됨.
- `data/laws/edge_type_taxonomy_draft.md` + `scripts/build_edge_type_mapping.py`:
  ACTION 913그룹 **전수**를 edge_type에 매핑 완료(100%, 52,791/52,791회).
  최종 **64개 edge_type**(`EDGE_TYPE_ROOTS`가 최종 근거). v1(77개) →
  사용자 피드백으로 과분화 지적 → v2(53개, 대표 예시만) → 전수 매핑
  중 진짜 빠진 개념(COMPLIES, LENDS 등) 보충 → v3(64개, 전수 확정).
  v1→v2→v3 verb_groups 재작업에서 배운 대로 반대 극성은 끝까지 분리
  유지(APPOINTS≠DISMISSES, PAYS≠BORROWS≠LENDS, RESTRICTS≠EXEMPTS 등).
- 산출물: `data/laws/edge_type_mapping.jsonl`(root→edge_type 최종 매핑,
  root/count/members/edge_type 필드). "처분"(행정처분 SANCTIONS vs
  재산처분 DISPOSES)과 "임면"(임명+해임을 아우르는 말)은 문맥 없이
  못 갈라 `needs_context: true` + `edge_type_alt`로 표시해뒀다.
- 재실행: `PYTHONIOENCODING=utf-8 python scripts/build_edge_type_mapping.py`
  (classify_edge_roots.py 먼저 실행해서 verb_roots_action.jsonl 갱신한
  뒤 돌려야 함).

## 4단계: 조/항 구조 파싱 + SVO 추출 (1차 구현 완료)

### 왜 "진짜" 의존구문분석기를 안 쓰는가
kiwipiepy 0.23.2(model_type="cong")를 직접 까봤는데 주어-동사 화살표
같은 의존관계 자체는 안 준다(형태소·격조사 태깅까지만). KLUE-DP 같은
통계적 한국어 의존구문분석기를 붙이는 방법도 검토했지만, **이
프로젝트가 폐쇄망으로 옮겨갈 계획**이라 무거운 모델 가중치를 새로
들이면 유지보수 부담만 커진다는 사용자 판단으로 기각 — 대신 격조사
(JKS/JKO/JX)를 규칙으로 해석하는 결정론적 방식으로 감.

### `src/graphdb/nlp/law_structure.py` — 조/항/호 파서
- `##### 제N조(의M) (제목)` 헤더, `**①**` 류 원문자 항 마커, `1\.`/`가\.`
  호/목 목록을 정규식으로 파싱. `## 부칙` 이후(조번호가 1부터 다시
  시작하는 별도 섹션 — 시행일/경과조치/다른 법률 개정 등)는 잘라내야
  함 — 안 그러면 마지막 "삭제"류 빈 조문이 EOF까지 부칙 전체를 항
  본문으로 삼켜버리는 버그가 있었음(제449조 사례로 발견, 수정함).
  전체 60개 파일/3,775개 조문/10,466개 항, 빈 항 0개로 검증 완료.

### `src/graphdb/nlp/svo.py` — 격조사 기반 SVO 추출기
핵심 난제와 해결 (전부 실제 법령 문장으로 테스트하며 발견한 버그들 —
처음 짠 버전은 셋 다 틀렸었음):

1. **목적어의 화제화(topicalization)**: "원장은 국회의 동의를 받아
   대통령이 임명한다"에서 "원장"은 JKS가 아니라 JX(은/는)만 붙어있고
   진짜 주격은 "대통령이" — "원장"은 "임명하다"의 목적어가 화제화된
   것("원장을" 생략). 규칙: 한 문장 안에서 JX(topic)와 JKS(subj)가
   **둘 다** 나오면 JKS가 진짜 주어, topic은 목적어로 재배정. 버그였던
   부분: 목적어(obj)를 절 경계에서 안 지웠더니 이전 절의 목적어가
   새 주어 등장 이후까지 새어 들어왔음 — **새 JKS가 나오면 obj를
   초기화**하는 규칙으로 수정.
2. **양상(의무/금지/재량) 판정 범위**: 실측 태그 시퀀스는 원래 가설과
   다름 — 재량=`NNB(수)+VA(있)`(최우선, 부정이 앞에 있어도
   재량 — "~하지 아니할 수 있다"=재량), 금지=`EC(지)+VX(아니하|못하)`,
   의무=`EC(어야)+VX(하)`. 버그였던 부분: 양상 탐지 윈도우가 문장 끝까지
   퍼져서 "A하며 B되지 아니한다"에서 B의 금지 표지를 A가 잘못 물려받음
   — **다음 동사구 시작 전까지만** 보도록 수정.
3. **"등" 처리**: "자회사등"의 "등"이 NNB(의존명사) 태그라 명사구
   연결 규칙에서 빠져서 "자회사등은"의 주어 인식이 실패했음 — "등" 특례
   추가.
4. **능동/피동 방향 정규화**: XSV 파생접미사가 "되다"/"받다"(피동)면
   agent/patient를 스왑. "~에 의하여" 행위자 명시구가 있으면 그걸
   agent로 씀.
5. **전방조응 주어 공유**: "OO를 거쳐 XX가 명한다"처럼 진짜 주어(JKS)가
   뒤쪽 절에 한 번만 나오고 앞선 절이 공유하는 경우 — 왼쪽→오른쪽
   한 번 훑기로는 못 잡아서, 문장 단위 사후 보정 패스(`_backfill_forward_subject`)
   로 처리.

**아직 안 된 것**: 호/목 열거형 목적어 분리("및/·/쉼표"로 나열된
목적어를 개별 엔티티로 쪼개기), **조건절 텍스트 추출**("제1항에도
불구하고", "~하는 경우에는" 같은 조건절 원문 — `condition` 필드로
들어가야 함, modality와는 별개).

## 엔티티(노드) 스키마 + 그래프 구조 (설계 확정, 적재는 미착수)

### 엔티티 스키마: `data/laws/entity_schema_draft.md`
동사와 달리 명사는 개방집합이라 verb_groups 때처럼 전수 어근
추출→그룹핑이 안 맞는다(사용자 판단) — `scripts/analyze_entities.py`로
전체 60개 파일 NNP/복합명사/단일NNG 빈도만 근거자료로 뽑고
(`data/laws/entity_noun_frequency.json`), 실제 카테고리 분류는 형태소
분석에 안 묶고 직접 설계했다.

- v1(27개 NodeLabel, 대분류별 세분화) → 사용자 지적: "Consumer" 같은
  라벨은 노드의 본질적 타입이 아니라 특정 관계 안에서의 일시적 역할 —
  edge_type 정리 때 배운 "같은 기능이면 합치고 세부는 property로"
  원칙을 노드에도 적용해야 함. v3에서 6개(Organization/Person/
  LegalDocument/Article/Concept)로 줄였다가, 아래 그래프 구조 논의
  끝에 **v4에서 Article도 제거해 최종 4개로 확정**: `Organization`
  (+`category`), `Person`(+`role_hint`), `LegalDocument`(+`doc_type`),
  `Concept`(+`concept_type`). 속성값(금액/기간 등)은 여전히 노드화 안 함.

### 그래프 구조: 엔티티 직접 연결, 조문은 순수 엣지 속성 (트리 아님, 이 프로젝트의 핵심 설계 판단)

**왜 이렇게 됐는지 — 세 번 뒤엎은 끝에 나온 결론.**

1. 사용자가 예전에 만들어본 구조는 `Law -[:CONTAINS]-> Provision`(조문,
   항/호는 별도 노드 없음) 밑에 `Provision`이 관계를 1:N으로 소유하고
   각 관계가 `{actor, action, condition}`을 갖는 트리형이었는데, 이
   트리 형태 자체가 "이상하다"고 느껴서 새 구조를 테스트해보려고 이번
   세션 작업을 시작함.
2. 1차 시도(기각): `Article -[:ASSERTS]-> Relation -[:AGENT/TARGET]->
   Entity`로 관계를 재질화(reify)하는 안을 제안했는데, 이건 **Relation이
   Provision 역할을 그대로 이어받아 트리를 재현한 것**이라 바로 잡힘 —
   "관계가 조문에 종속된다"는 원래 구조의 문제를 이름만 바꿔서 갖고
   온 것.
3. 2차 시도(기각): 관계 재질화는 버리고 `(Entity)-[:EDGE_TYPE {source_law,
   article_no, ...}]->(Entity)`로 조문을 엣지 속성화했는데, `Article`
   노드는 "구조적 단위"라는 이유로 그대로 남겨뒀음(참조용 그래프로).
   그런데 "이 법의 내용을 그래프로 만드는 것"이 목적이라면, Article
   노드가 실제로 하는 일이 없다는 게 드러남 — 조문 원문이 필요하면
   그래프 노드가 아니라 `data/laws/raw/*.md`를 `article_no`로 찾아보면
   충분하다. "구조적이라 예외"라는 근거 자체가 사실 "엔티티가 아니라
   인용 메타데이터"라는 뜻이었음.
4. "제10조는 제5조를 준용한다" 같은 조문 간 참조도 Article↔Article
   엣지가 아니라 **적재 시점 인용 전파**로 처리하기로 함 — 제5조에서
   뽑힌 관계들에 `article_no: 10`을 추가 인용으로 얹어주는 방식(그래프
   구조는 안 늘어남). "정의차용" 같은 단순 인용(참조 대상 법령이 어차피
   별도로 그래프에 들어감)은 스킵.

**최종 확정 구조**(CLAUDE.md에도 요약돼 있음):
```
(대통령:Organization)-[:APPOINTS {
    source_law: "감사원법", article_no: 4, paragraph_no: 1,
    condition: null, modality: "없음", voice: "능동"
}]->(원장:Organization)
```
Article/Relation/Assertion/Provision 같은 "관계를 소유하는" 노드가
그래프에 전혀 없다. 조문 출처는 엣지의 **속성**일 뿐 — 순회해서
거쳐가야 하는 노드가 아니다. "이 조문에서 나온 관계 전부"는
`article_no` 속성 필터(인덱스 걸면 성능 문제없음)로 해결.
